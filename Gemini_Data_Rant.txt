Okay, after reviewing backend/src/handlers/script_handlers.rs, it seems the route PATCH /api/scripts/:script_id/content (which saveContentToServer in the frontend calls) is not currently defined or handled in your backend.
The existing routes in script_routes are:
/upload (for uploading DOCX files and getting them parsed by Gemini, returning the ParsedScript structure)
/create_script_from_parsed (for taking a ParsedScript structure and creating the scripts and associated blocks entries in the database)
This is a critical missing piece for persisting ongoing edits from the TipTap editor to your database.
To summarize:
y-websocket + backend/src/ws.rs: Handles real-time collaboration by syncing Yjs document updates between connected clients. It does not save to PostgreSQL.
y-indexeddb (in frontend): Saves the Yjs document to the browser's local storage. This is why you see content in browsers that have previously interacted with the script.
Saving to PostgreSQL (Current State):
Initial Creation: The flow for upload_and_parse_script followed by create_script_from_parsed_handler (which calls create_script_from_parsed from lib.rs) does save the initial scripts record and its initial blocks to PostgreSQL.
Ongoing Edits: There is no backend endpoint or logic currently implemented to handle the PATCH requests from saveContentToServer in your Editor.tsx. This means any subsequent edits made in the TipTap editor, while synced between collaborators via WebSockets and saved to their local IndexedDB, are not being saved back to the PostgreSQL blocks table.
This explains why:
Scripts (metadata) exist in the scripts table (created via the initial upload/parse flow).
blocks and edits are empty in PostgreSQL for scripts that were only edited after initial creation, or if the initial block creation from ParsedScript failed.
You can see "mostly" the texts in different browsers if those browsers participated in the Yjs session (via WebSocket) or opened the script when their IndexedDB was populated. The source of truth for these edits is currently fragmented across client-side IndexedDB stores and the live Yjs session state.
Solution Path:
You need to implement the backend handler for PATCH /api/scripts/:script_id/content. This handler should:
Accept the script_id from the path and the content payload (which is currently editor.getHTML()) from the request body.
Parse/Transform the received content: editor.getHTML() will give you HTML. Your blocks table expects structured JSON for its content field (based on block_type). You'll need logic in the backend to:
Parse this HTML.
Identify or determine the block_type for each piece of content.
Transform it into the correct JSON structure for that block_type.
This is a non-trivial step. A simpler approach might be to have the frontend send a more structured format if possible (e.g., TipTap's JSON export, or Yjs document as JSON), but that would require frontend changes too.
Update the blocks table:
For the given script_id, you'll likely need to:
Fetch existing blocks.
Compare with the incoming content.
Update existing blocks, delete blocks that are no longer present, and add new blocks. This can be complex to do efficiently and correctly to maintain order and integrity.
Alternatively, a simpler (but potentially less granular) approach for a PATCH could be to replace all existing blocks for that script_id with the new set of blocks derived from the payload. This is easier to implement but loses fine-grained history unless your edits table logic is very robust.
Optionally, create entries in your edits table to log these changes.
This is the missing link for true persistence of edits made after a script's initial creation from a DOCX file.
